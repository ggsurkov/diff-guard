# Ограничения для AI-агентов, работающих над diff-guard

Эти правила — жёсткие рамки для кода, который генерирует AI-агент в этом
репозитории. Их нарушение — повод переписать решение, а не задокументировать
исключение.

## Токены и размер контекста

- Не вставлять в промпт WebLLM весь diff целиком без ограничения размера —
  всегда резать/chunk'ать по файлам или хункам и явно сообщать пользователю,
  если diff обрезан. Локальные модели (3B–8B, запускаемые в браузере) имеют
  контекст в разы меньше серверных — на это и рассчитывать бюджет.
- Системный промпт держать компактным и стабильным (чтобы кэшировался KV-cache
  движка между запросами), не генерировать его заново с вариациями на каждый
  вызов.
- Не просить у модели ничего, что не будет использовано в UI: каждое поле в
  запрошенной JSON-схеме ответа должно рендериться хотя бы одним компонентом.

## Память и WebGPU

- Одновременно в памяти — не больше одного загруженного WebLLM-движка/модели.
  Перед загрузкой новой модели явно выгружать предыдущую (`engine.unload()`),
  а не полагаться на GC.
- Не держать в `$state` полные снапшоты больших промежуточных структур
  (токенизированный diff, сырые логиты и т.п.) дольше, чем нужно для текущего
  шага пайплайна — освобождать ссылки после использования.
- Песочница анимаций (canvas/iframe) должна останавливать `requestAnimationFrame`
  и WebGPU/WebGL-контексты при закрытии/скрытии компонента (`$effect`
  cleanup) — висящие RAF-луперы в закрытых вкладках истории — частый источник
  утечек в расширениях.
- Не грузить модель заранее "на всякий случай" при открытии side panel — 
  инициализация WebLLM только по явному действию пользователя (запуск
  анализа), т.к. это дорогая по памяти и трафику операция.

## Неблокирующий UI / стриминг

- Вывод модели рендерить потоково (`chunk`-callback WebLLM →
  обновление `$state`), не ждать полного ответа перед показом хоть
  чего-то пользователю.
- Любая операция дольше ~50мс (парсинг большого diff, токенизация) — не в
  main thread синхронно. Использовать `requestIdleCallback`/чанкование цикла
  или выносить в отдельный воркер, если объём оправдывает сложность.
- UI не должен блокироваться (заблокированные кнопки/скролл) на время
  генерации — пользователь должен иметь возможность прокручивать diff и
  читать уже пришедшие карточки, пока генерация продолжается.

## Изоляция стилей и песочниц

- Сгенерированный/пользовательский CSS для превью анимаций — только внутри
  `<iframe sandbox="allow-scripts">` (без `allow-same-origin`), никогда не
  инжектить `<style>` с недоверенным содержимым в DOM самого расширения.
- Компоненты ревью-карточек — свои CSS-классы с уникальным префиксом
  (например, `dg-`), не полагаться на глобальные стили страницы-хоста, т.к.
  side panel рендерится в изолированном extension-контексте, но внутренние
  компоненты друг друга не должны конфликтовать по классам при динамической
  генерации UI.
- Данные, приходящие из ответа модели, перед вставкой в DOM всегда проходят
  через Svelte-байндинг (`{expression}`), никогда не через `{@html}` без
  санитизации — модель генерирует текст, который в теории может содержать
  разметку.

## Общее

- Не добавлять сетевые вызовы к сторонним API анализа/телеметрии — весь
  анализ diff'а обязан оставаться локальным (см. `.agents/project.md`).
  Единственный легитимный сетевой трафик — загрузка весов модели с CDN
  WebLLM/Hugging Face при первом запуске.
- Не отключать `strict`/типизацию (см. `.agents/skills/typescript.md`) и не
  ослаблять CSP (см. `.agents/skills/chrome-extension.md`) ради удобства
  разработки — эти ограничения продуктовые, а не временные.
